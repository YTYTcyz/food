## 3. 每轮的固定操作

每轮只创建一笔目标订单，编号不要复用：

```js
await sprint1.start('S1-01')  // 下单前保存已有成果基线
```

在页面正常选菜、提交订单。确认出现成功弹层或等待页，尽快在到期前执行：

```js
await sprint1.created()      // 记录本单ID、价格、热量、起止时间及创建后的成果
```

按该轮场景操作完成后，执行相应的一种预期：

```js
await sprint1.finish('early')     // 页面点击“不想吃了”提前成功
// 或 await sprint1.finish('timeout')   // 正常到期或重开补结算
// 或 await sprint1.finish('given_up')  // 到期前明确选择“还是吃了”
```

接着重放同一订单，验证终态和奖励不可重复改变：

```js
await sprint1.repeat()       // 按 complete、giveUp、lookup、get 重放同一终态订单
await sprint1.copy()         // 复制本轮报告，粘贴到你的操作记录或反馈消息
```

- `INCOMPLETE`：还有阶段没执行；start、created、finish 后出现此值正常。
- `API_CHECKS_PASS`：采集到的 API 核对项全部通过；仍须完成第 5 节数据库只读核对和页面人工观察。
- `FAIL`：查看 `checks` 中 `passed:false` 的项；保留报告，反馈实际结果，不修改数据来凑预期。
- 命令报错：该次采集未完成，不能当作通过。网络恢复后重试同一命令即可；已保存的创建/结算/重放阶段不覆盖。
- 重开/重新编译后：重新粘贴整个助手，再执行 `await sprint1.resume('原编号')`。使用 `await sprint1.report()` 查看记录。
- 新一轮复验用新编号，例如 `S1-01-r2`；旧记录保留在当前身份的本机存储中。

助手报告只保存本轮内部用户 ID、订单 ID、金额/热量/次数、日期、拼图位置及徽章证据，不保存昵称、日记、体重、订单备注、照片或文件链接。它不记录账号凭据。

## 4. 必做场景

### S1-01：提前成功、活动订单互斥与重复结算

1. `start('S1-01')` 后，在商家 A 选菜；另在商家 B 留一点购物车内容，再回 A 下单。核对金额=商品合计+1.50元；所有支付方式均为模拟，无真实扣款。
2. 弹层停留约20秒再进入等待：倒计时已经减少，不应重新从05:00开始。执行 `created()`，记录订单 ID；此时按第 5 节查本单拼图进度应为0条。
3. 回 B 的订单页尝试提交：应提示已有进行中的挑战，去查看后回到 A 的同一订单。B 的购物车内容保留，不能新增第二个 waiting 订单。云数据库按本 userId 和 `status=waiting` 查询，应恰好1条。
4. 在到期前点击“我已不想吃了，取消订单”。结果页应展示本单金额、热量及结算后的次数/等级/拼图步骤。
5. 执行 `finish('early')`、`repeat()`、`copy()`；按第 5 节核对数据库。

通过：`completionReason=early`，服务端 `completedAt<expiresAt`；成果只加一次，A 本次购物车已清除、B 保留，重复请求不新增奖励。

### S1-02：完整等待5分钟自动成功

1. 查看上一轮成功结果后回首页，执行 `start('S1-02')`，正常新建订单并执行 `created()`。
2. 不点击提前成功或放弃；等待真实5分钟结束，观察自动进入成功结果。不要修改本机或服务端时间。
3. 执行 `finish('timeout')`、`repeat()`、`copy()`，完成数据库核对。

通过：`completionReason=timeout`；`completedAt` 与 `expiresAt` 相同，奖励规则与提前成功一致。本地倒计时到零不是主动提前成功。

### S1-03：到期前放弃

1. `start('S1-03')` 后正常新建订单、执行 `created()`。
2. 到期前打开放弃弹层，先选“再坚持下”：应继续等待；再打开，明确选“还是吃了”：应结束本次挑战回首页。
3. 执行 `finish('given_up')`、`repeat()`、`copy()`，完成数据库核对。

通过：状态为 `given_up`，`givenUpAt<expiresAt`，本单钱包流水和拼图进度均0条，已有成果/拼图/徽章不减少；后续 complete 也不能把这单变成成功。若操作抵达服务端时已到期，本轮应记录为场景未满足，另用新编号重做，不能改写订单。

### S1-04：退出后重开补结算

1. `start('S1-04')` 后正常新建订单、执行 `created()`，先复制一次创建报告以便保留订单 ID。
2. 退出小程序，超过该单 `expiresAt` 再打开。开发者工具可以停止运行后重新编译，但**不清存储**；真实退出/重开也可在设备上补验。
3. 观察挑战入口或待查看结果，进入成功结果页。重新粘贴助手，执行 `resume('S1-04')`，然后 `finish('timeout')`、`repeat()`、`copy()`。

通过：重开后恢复同一订单，钱包仅加一次；成功时刻仍为原 `expiresAt`，不是重开时刻。读取接口也可触发补结算，所以先记录页面恢复结果，再执行 finish，避免助手掩盖页面恢复问题。

### S1-05：创建响应丢失，用原请求恢复

本场景模拟“云端已处理，客户端没收到响应”，不代表全部真实弱网情况已经验收。

1. 执行 `start('S1-05')`，在订单页准备好商品。
2. Console 执行 `await sprint1.loseNextCreate()`，然后在页面提交一次。该请求会真实到达云端，但助手只丢弃这一次返回值；不会自动创建其他订单。
3. 页面应提示提交未确认、显示“查询并重试”，购物车和原内容仍在。点击重试：先按原 key 查询，恢复同一个订单，不能重复创建。
4. 恢复后执行 `created()`，再在页面提前成功；执行 `finish('early')`、`repeat()`、`copy()`。
5. 云数据库 `challenge_orders` 按报告中的本 userId 与 `idempotencyKey` 查询：恰好1条；结合第 5 节核对奖励。

通过：响应丢失时不提前清购物车、不宣称已到账；恢复用同一 key 与原内容，最终一单一份奖励。

### S1-06：离开页面后，迟到响应不能打断当前操作

响应延迟仅作用于下一个匹配请求，默认8秒；真实云端请求照常执行。未触发时可执行 `sprint1.restoreCalls()` 取消，或重新编译恢复原调用。设置后立即按该场景操作，期间不要执行助手采集命令抢先消耗匹配请求。

**S1-06a，订单页：** 新编号采基线、选菜，执行 `await sprint1.delayNext('create')`；提交后8秒内返回商家。等待返回值到达，当前页面不应被弹层或导航打断，购物车仍在。重新进入原商家订单页，应按原 key 恢复；继续 `created()`，提前成功、finish/repeat/copy。成功弹层也可切后台再回，仍能进入同一挑战，倒计时不重置。

**S1-06b，等待页：** 新编号采基线、下单并执行 `created()`；执行 `await sprint1.delayNext('complete')`，页面点击提前成功后，立即进入日记等工具。8秒后应仍停留工具，输入内容不丢失；返回挑战入口后看到实际成功结果。继续 finish/repeat/copy。

**S1-06c，结果页：** 新编号采基线、下单并执行 `created()`；执行 `await sprint1.delayNext('get')` 后立刻点击提前成功。当结果页仍在加载时，切到后台或其他页面；在后台等待返回。此时数据库 `user_state.pendingResultOrderId` 应仍是本单；回前台看见渲染好的结果后才清除。继续 finish/repeat/copy。如果延迟被等待页定时 get 消耗、结果页没有出现加载窗口，记录“未复现”并在新一轮重做。

三项都须分别记录页面观察；助手的数值通过不代表导航/草稿行为已经通过。

## 5. 云数据库只读核对

在开发者工具云开发面板中打开现有环境的数据库，用条件筛选；**只查询，不编辑、不删除**。报告 `evidence.userId` 是内部用户 ID，`evidence.created.order._id` 是本轮订单 ID。

每轮 S1-01～04 至少完成以下核对，S1-05/06 也核对最终唯一性：

1. **创建后：** `memorial_card_progress` 按 `challengeOrderId=本单ID` 查询应0条；助手已核对此时 wallet_ledger 无本单流水、统计没有增加。页面创建报告必须在到期前取得。
2. **成功后：** `wallet_ledger` 按 `orderId=本单ID` 查询恰好1条；`memorial_card_progress` 按 `challengeOrderId=本单ID` 查询恰好1条。不能只按 `_id` 找到一条就认定不存在重复。
3. 两条记录的 `userId` 均等于本轮内部用户 ID；钱包 `amountCents` 等于订单总金额，`caloriesKcal` 等于订单热量，`effectiveAt/successDate` 等于订单实际成功时间/北京时间日期。
4. 拼图进度 `cardId` 等于 `order.result.cardId`，`stepIndex` 等于 `order.result.cardStep`；有效时间、日期与订单相同。`memorial_cards` 的相应卡片步骤与报告一致。
5. 本轮未换图，进度中的网格/布局版本应与卡片一致；该进度 `revealedTileIndexes` 数量应为 `floor(N×k/7)-floor(N×(k-1)/7)`，其中 N 为总块数、k 为本轮完成后的步骤。索引不重复、均在0～N-1范围内，且对应本轮新增亮块。创建前没有卡时 k=1；已有卡从报告 `before.card.currentStep` 的下一步计算。不可把已有第6步卡片当作新卡验收。
6. **放弃后：** 本单 wallet_ledger 和 memorial_card_progress 均0条；不应存在该单成功结果。
7. **repeat 后：** 再查相同条件，条数及记录保持原样；成功单仍1/1，放弃单仍0/0。如果本轮达到徽章门槛，`user_achievements` 按本 userId+code 查询应恰好1条，已有解锁时间不变。
8. `user_state` 按内部 userId 查询，成果值与报告 `after.state` 一致；`daily_successes` 按本 userId 和实际成功日期查询，三个增量分别是成功次数+1、金额+本单金额、热量+本单热量。放弃不增加，原记录不存在时继续保持不存在。

推荐记录格式：`S1-01：创建进度0；成功流水1/进度1；重放后1/1；归属/时间/金额/步骤/新增亮块一致；页面通过`。有差异时附订单 ID、错误项、时间和必要截图，不发送私人正文或身份凭据。
