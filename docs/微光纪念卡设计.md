# 不忍了微光纪念卡设计

2026-09-09确认：仍按7次挑战成功集齐，同一天可推进多次。手动打卡是独立功能，不推进拼图。

## 图片与网格

完整保留JPG/PNG的长宽比例，格子覆盖在同一比例的图片上，不把图片拉成方形，也不要求格子严格正方形。

- 短边固定6格，长边为round(6×长边像素/短边像素)，最多24格。总数36～144块。
- 1080×1080为6列×6行，36块；1980×1280为9列×6行，54块；1280×1980为6列×9行。
- 超长图仍完整等比展示，只限制格子数量，格子会更长。预览同时限制最大宽高，完整图片居中，外围空白不计入拼图。
- 2026-09-11取消用户原图10MB门槛，尝试微信能解码的图片；自动等比缩小、必要时转JPG/降质量，成品长边最多2048px且目标不超过2MiB，不放大小图、不裁内容。较小PNG保透明度，转JPG铺白底，动图保存静态画面；原件保持不变。头像独立保留方形裁剪，无法解码的文件提示重试/换图。
- 服务器读取成品实际格式、尺寸及EXIF方向；客户端传入的尺寸不作为奖励依据。设备上的方向、缩放和显示表现需要真机验证。

## 7次均分

总块数为N，第k次成功后累计点亮floor(N×k/7)块；本次增加量是本次累计减去上次累计。

- 36块：5、5、5、5、5、5、6。
- 54块：7、8、8、7、8、8、8。
- 66块：9、9、10、9、10、9、10。

每次相差最多1块，第7次必定全部点亮。从未亮位置抽取并保存，重试不重抽。提前成功/到时成功都只推进一次；放弃不推进。

## 生命周期与换图

无活动卡 → 成功时建卡并推进 → 第7次自动收藏锁图 → 下一次成功开新卡。尚无可用图库时，卡片使用6×6占位并保存进度，首次实际图片可用时按照下面的换网格规则配置图片与亮块。

进行中换图保留currentStep。新旧网格行列相同，保留已亮位置；网格行列改变，按新N和原currentStep重算亮块数，使用卡ID+新网格尺寸确定稳定重排，layoutRevision加一。不存在为了保留方格位置而裁剪新图的处理。换图不增加订单、成功次数、钱包或完成卡数。完成卡不可换图，可设为主页背景；主页背景也等比显示。

系统默认card-01，首批6张本地素材位于data/assets/memorial-presets/v1/。运行node scripts/build-memorial-presets.js读取实际尺寸，更新deploy/memorial-presets.template.json，不推测fileID。已有卡固定图片和尺寸快照，后来改图库记录不会替换既有卡图。

## 界面与持久化

上方动态网格，下方已完成X/7次、已点亮/当前总块数、目标体重进度与陪伴文案。目标进度来自体重记录，与拼图完成进度分开。网格与图片必须共享同一宽高，禁止用aspectFill裁掉拼图边缘。

memorial_cards保存图片尺寸、行列、总块数、布局修订、成功步骤和亮块。memorial_card_progress按订单唯一，保存此次亮块及当时的布局修订/行列/总数，历史位置应在当时布局下解释；换图不修改历史奖励。成功结算与换图同用事务，发生并发时保留实际成功步骤。详情见《数据库设计》《接口契约》。
